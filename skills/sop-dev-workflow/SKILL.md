# sop-dev-workflow — 通用软件开发流程 Skill

## 一、核心定位与哲学

- **名称**：`sop-dev-workflow`
- **输入**：自然语言需求（新建项目 / 新增模块 / 删除模块 / 需求变更 / 性能优化 / 依赖升级 / 配置变更 / 版本回滚 / 只读查询）
- **输出**：静态工程资产（设计文档、用户手册、源代码、冒烟测试、单元测试、契约测试、验收测试、配置模板、模块注册表、迁移脚本、审计报告）
- **不输出**：编译中间产物（`.o`/`.pyc`/`.class`）、运行时数据（`.db`/`.log`）、依赖缓存（`node_modules/`）

### 三大支柱

1. **多角色协作**：架构师（定职责与边界）、设计师（定义接口签名与内部逻辑）、评审员（闭卷考试验证完备性）、开发（编码+冒烟）、测试（独立验证）各司其职
2. **闭卷考试**：评审员不看任何实现代码，仅凭设计文档模拟调用，验证文档完备性
3. **契约驱动**：接口先行，测试独立，通过契约测试验证模块间兼容性

### 核心原则

- **测试独立性原则**：开发Agent只负责写代码和冒烟测试（验证可运行性），测试Agent独立负责全部逻辑验证测试（单元/契约/验收），两者互不触碰对方领地
- **版本管理原则**：所有代码、文档、测试用例均通过 Git 进行版本管理，每个 Phase 的关键产出独立提交，确保可追溯性

## 四、Git 版本管理规范

### 4.1 核心原则

- **全量纳入版本控制**：所有文档（`/docs`）、源码（`/src`）、测试用例（`/tests`）、配置模板（`/configs`）、注册表（`MODULE_REGISTRY.json`）均须纳入 Git 管理
- **编译产物不入库**：`/build/`、`*.o`、`*.pyc`、`*.class` 等编译中间产物一律不提交
- **运行时数据不入库**：`*.db`、`*.sqlite`、`*.log`、`*.pid` 等运行时生成文件一律不提交
- **敏感配置不入库**：含真实密码、密钥的 `.env` 文件一律不提交，仅提交 `.example` 模板

### 4.2 提交规范（强制）

每次提交必须遵循以下格式：

```
<type>(<scope>): <subject>

[optional body]

[optional footer]
```

**Type 类型定义：**

| Type | 说明 | 示例 |
|------|------|------|
| `phase` | 完整 Phase 交付 | `phase(arch): 完成架构设计并初始化注册表` |
| `design` | 设计文档变更 | `design(module_a): 补充超时处理边界条件` |
| `code` | 源码变更 | `code(module_a): 实现数据采集核心逻辑` |
| `test` | 测试用例变更 | `test(module_a): 增加边界值单元测试` |
| `fix` | Bug 修复 | `fix(module_b): 修复空指针异常` |
| `refactor` | 重构（不改功能） | `refactor(module_a): 优化循环逻辑` |
| `docs` | 文档变更 | `docs: 更新架构图中的数据流描述` |
| `config` | 配置变更 | `config: 修改数据库连接池大小` |
| `chore` | 杂项（构建/工具） | `chore: 更新 .gitignore` |

**提交粒度要求：**

| Phase | 提交节点 | 建议提交内容 |
|-------|----------|--------------|
| Phase 1 完成 | `phase(arch): 完成架构设计与模块注册表` | `architecture.md` + `MODULE_REGISTRY.json` + `.gitignore` |
| Phase 2 完成 | `phase(design): 完成模块X设计文档` | 每个模块的设计文档独立提交 |
| Phase 3 完成 | `phase(review): 模块X评审通过` | 评审报告（可选提交，建议保留） |
| Phase 4 完成 | `phase(code): 模块X编码+冒烟测试通过` | 源码 + 冒烟测试 |
| Phase 5 完成 | `phase(test): 模块X单元/契约测试通过` | 测试用例 + 测试报告 |
| 最终交付 | `phase(delivery): 全量验收测试通过，准备交付` | 全部产出 + 最终测试报告 |

### 4.3 分支策略（建议）

| 分支 | 用途 | 说明 |
|------|------|------|
| `main` | 稳定交付分支 | 仅接受经过 QA 全量验收通过的代码，每个提交对应一个完整交付版本 |
| `develop` | 开发主分支 | 所有 Phase 产出先合并至此，用于集成验证 |
| `feature/module-<X>` | 模块特性分支 | 从 `develop` 切出，完成单个模块的 Phase 2→3→4→5 后合并回 `develop` |
| `hotfix/<description>` | 紧急修复分支 | 从 `main` 切出，修复线上紧急 Bug 后合并回 `main` 和 `develop` |

### 4.4 回滚策略

当触发"版本回滚"场景时：

1. 开发Agent执行 `git revert` 或 `git reset --hard <tag>` 回退代码
2. **设计文档不做回退**（文档代表当前最新设计意图，保持最新）
3. 测试Agent重新执行上次交付的验收测试套件
4. 产出回滚报告，记录回滚原因和影响范围

## 七、评审员（Reviewer）详细定义

### 本质定位

评审员不是"文档校对员"，也不是"代码审查员"，而是**"可执行性验证员"**。它的唯一任务是回答一个问题：**"如果一个陌生的开发Agent从未看过实现代码，仅凭这份设计文档，能否独立且正确地完成编码？"** 如果答案为"能"则通过，如果"不能"或"不确定"则打回。

评审员是**流程中最上游的质量闸门**——它不参与编码也不参与测试，只在编码开始前确保设计文档的质量。

### 闭卷考试执行流程（3步走）

| 步骤 | 动作 | 说明 |
|------|------|------|
| **第1步：接口签名提取** | 从设计文档的"对外接口签名"章节中提取函数名、入参列表（名称+类型）、出参列表（名称+类型）、错误码/异常列表 | 若任何一项缺失或不明确 → 直接判 `fail` |
| **第2步：模拟调用尝试** | 尝试写出调用该模块的完整代码片段，包括如何初始化、如何传参、如何处理返回值、如何处理异常 | 若不知道如何初始化、参数类型模糊、返回值不确定、错误码列表为空 → 判 `fail` |
| **第3步：完备性核查** | 逐条核对检查项清单：接口签名完整性、初始化方式说明、边界条件说明、时序/调用顺序、上游依赖声明 | 但凡有一项不通过 → 判 `fail` |

### 评审员行为红线

- 禁止"脑补"：发现文档缺失必须判 `fail`，不得自行假设
- 禁止提优化建议：`comments` 仅用于"缺失/歧义/矛盾/不可实现"
- 只评审当前模块：不评审上游模块的正确性
- **双格式产出**：评审报告必须同时产出 JSON（机读，遵循 Schema）和 Markdown（人读，表格化呈现），两者内容一致、仅格式不同
- **PASS with notes（补）**：判定 pass 仍可附带"非阻断遗留"清单——每条标注【位置/影响/建议回环方式】；遗留进入开发阶段必须回环（§10 红线 19），评审员不做"脑补式未知"放行：凡"不可闭卷实现"一律 fail（不因细节小就降级）
- **增量设计评审（补）**：增量/里程碑设计允许引用上游已评审契约而不重复定义（评审员按"上游可读契约清单"核对一致性）；评审对象可为多份文档（如同一里程碑的前后端契约）；评审范围 = 增量本身 + 与上游一致性，不评审上游正确性

## 八、测试Agent（Tester）详细定义

### 本质定位

测试Agent是**独立的质量验证角色**，与开发Agent完全分离。它不写任何生产代码，只负责验证代码的正确性。

测试Agent采用**"测试先行"**方式工作：

1. 先读设计文档（理解期望行为）
2. 再写测试用例（定义验证标准）
3. 等开发提交源码后执行（对比预期与实际）
4. 发现不一致则打回（附Bug报告）

### 测试层级与职责

| 测试类型 | 存放位置 | 目的 | 执行时机 | 说明 |
|----------|----------|------|----------|------|
| **单元测试** | `/tests/unit/` | 验证各模块内部逻辑正确性 | 每个模块交付后 | 覆盖率 ≥ 80% |
| **契约测试** | `/tests/contract/` | 验证上下游模块接口互通 | 上游模块交付后 | 基于接口签名编写 |
| **验收测试** | `/tests/acceptance/` | 验证端到端业务场景满足需求 | 全部模块交付后 | 基于全部设计文档 |

### 测试执行流程

```
测试Agent按 development_order 顺序处理每个模块：
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│ 【单元测试阶段】                                        │
│ 1. 读当前模块设计文档                                   │
│ 2. 基于接口签名编写单元测试用例                         │
│ 3. 执行单元测试                                        │
│ 4. 有失败 → 生成Bug报告打回开发Agent修复               │
│ 5. 全部通过 → 进入契约测试阶段                         │
└─────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│ 【契约测试阶段】                                        │
│ 1. 识别当前模块依赖的上游模块                          │
│ 2. 基于上游模块的接口签名编写契约测试用例              │
│ 3. 执行契约测试                                        │
│ 4. 有失败 → 生成Bug报告打回开发Agent修复               │
│ 5. 全部通过 → 标记当前模块完成                         │
└─────────────────────────────────────────────────────────┘
    │
    ▼
所有模块完成后：
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│ 【验收测试阶段】                                        │
│ 1. 基于全部设计文档编写端到端验收测试用例              │
│ 2. 执行全量验收测试                                    │
│ 3. 有失败 → 生成Bug报告打回开发Agent修复               │
│ 4. 全部通过 → 产出最终测试报告                        │
└─────────────────────────────────────────────────────────┘
    │
    ▼
交付
```

### 测试Agent行为红线

- 严禁修改源码
- 严禁修改冒烟测试
- 必须先确认冒烟通过
- 不越级：不得在契约测试或验收测试未通过时声称"已通过"
- **双格式产出**：测试报告必须同时产出 JSON（机读）和 Markdown（人读），两者内容一致
- **测试分层与断言演进（补）**：随里程碑推进，既有断言更新权归测试Agent（红线 16）；更新须注明变更理由（如"占位徽章→demo 数据徽章"）；测试代码不得为通过而弱化断言（仍须验证语义）
- **子代理停滞接管协议（补）**：测试Agent（子代理）长时间无产出（如状态 running 但无测试进程/无文件时间戳更新）→ 主代理中断接管：接管执行其已产出的用例集合；报告注明"用例=测试Agent 产物，执行=主代理接管"；子代理会话可经 send_message 延续（复验/更新报告），不必重启
- **工具链连带升级（补）**：框架/构建升级（如 Vite 5→7）必须同步升级测试工具链（如 vitest 2→3，二者版本映射）并纳入该步验证命令——防止"全量隔离抖动"等隐性不兼容
- **报告命名与防覆盖（补）**：多模块/多里程碑 QA 报告独立命名（如 `qa_final_report_frontend_m3.json`），严禁覆盖同级既有交付报告；coverage 数字须注明统计集合（如"全绿集合重核算"）
- **mock 约定（补）**：jsdom 环境无 canvas——涉及 ECharts 的测试统一 `vi.mock` 后端图表模块；后端测试必须 mock provider/db（禁止真实网络），并发请求须 timeout 包裹；任何单条命令 120s 无输出即中止并记录（防停滞）
- **用户手册**：全量验收测试通过后，使用 `templates/user_manual.md.template` 模板生成用户手册 `/docs/user_manual.md`

## 九、全生命周期场景路由

| 场景 | 触发语示例 | 路由路径 | 关键动作 |
|------|-----------|----------|----------|
| **新建项目** | "开发一个XX系统" | 全量 Phase 1→5 | 完整产出，初始化 Git 仓库 |
| **新增模块** | "增加一个XX模块" | 局部重入 Phase 1→2→3→4→5 | 架构师更新职责边界 → 设计师定义接口 → 评审 → 编码 → 测试 |
| **删除模块** | "删除XX模块" | 依赖分析 → 自动/阻断 | 无人依赖：归档+删码+清理测试+回归；有依赖：阻断并提示 |
| **需求变更** | "修改XX功能" | 绿 / 黄 / 红 分级 | 绿（改内部逻辑，接口不变）：直改+定向测试；黄（跨模块，接口不变）：回退设计→重审→改码→全量回归；红（改接口）：阻断，提示V2重构 |
| **性能优化** | "优化XX速度" | 绿色增强版 | 改码+性能基准对比+定向测试 |
| **依赖升级** | "升级Python到3.11" | 红色全量重构 | 出影响清单 → 用户确认 → 全量 Phase 1→5 |
| **纯配置变更** | "改数据库连接池" | 绕过主流程 | 仅改配置文件，测试Agent冒烟测试 |
| **版本回滚** | "回退到V1.2" | 紧急通道 | Git回退 → 测试Agent重跑上次验收 → 出回滚报告（不改设计文档） |
| **只读查询** | "当前数据流是什么？" | 只读模式 | 仅读文档+代码，出分析报告，**不生成变更文件** |
| **轻量任务（绿-轻量）** | "把顶部标签去掉"（UI 微调/文案/图标/布局顺序/展示性调整） | 直改通道 | 仅约束：**构建零错误 + 冒烟通过 + 定向测试（受影响用例）**；免 Phase 5 全量 QA 报告；无新接口、不动数据逻辑 |
| **里程碑化执行** | "开始 M3"（既有需求分多里程碑推进） | 每里程碑独立 Phase 1→5 闭环 | 每里程碑 = 独立循环 + git tag 回退点（可停可回退）；架构文档维护里程碑总表（✅/🔄）；里程碑间不得跨阶段混提
> **绿色分级补充**：绿级再分两档——**绿-轻量**（上表，免全量验证，用户明确"简单任务不用验证"时直接走此档）；**绿-常规**（逻辑变更/跨模块，走完整测试）。分级判定权在用户裁决，裁决须记录进架构/设计文档（含撤销记录，如"已撤销：曾定 children 树形 → 改平级"）。

## 十、硬性红线（共 19 条）

1. **冻结旧契约**：严禁修改已交付模块的对外接口签名；确需修改必须走红色路径升级为V2重构。接口签名的修改权归**设计师**，但需经架构师确认职责边界是否随之变化。
2. **开发不写逻辑测试**：开发Agent仅编写冒烟测试（验证可运行性），严禁编写单元测试、契约测试或验收测试。
3. **评审不看代码**：评审员严禁读取 `/src/` 目录。
4. **测试不改源码**：测试Agent严禁直接修改 `/src/` 或 `/tests/smoke/`。
5. **物理隔离中间产物**：`.o/.pyc/.class/.db/.log` 等严禁出现在 `/src/` 或根目录。
6. **禁止越权建顶层目录**：开发Agent无权在 `/src/` 下创建顶层目录，须严格匹配注册表中的 `src_path`。
7. **接口变更必须升级**：任何人发现接口缺陷不得私改，必须由**设计师**发起"接口变更令"，经架构师确认职责边界后重新走评审流程。
8. **回滚不改文档**：版本回滚时设计文档保持最新，不做任何修改。
9. **评审员禁止脑补**：发现文档缺失必须判 `fail`，不得自行假设。
10. **评审员禁提优化建议**：只指出"缺失/歧义/矛盾/不可实现"，不评价风格或性能。
11. **评审员只评当前模块**：不评审上游模块的正确性。
12. **测试先行验证**：测试Agent在交付模块测试报告前，必须先确认冒烟测试通过，否则直接打回。
13. **测试不越级**：测试Agent不得在契约测试或验收测试未通过时，声称模块"已通过"。
14. **开发不碰验收测试**：开发Agent严禁创建或修改 `/tests/unit/`、`/tests/contract/`、`/tests/acceptance/` 下的任何文件。
15. **Git 提交规范**：所有 Git 提交必须遵循"提交规范"中定义的 type 和格式，每个 Phase 的关键产出独立提交，严禁将多个 Phase 的产出混在一次提交中。
16. **测试断言里程碑演进授权**：里程碑语义变更（占位→真实/徽章文案/模块计数/组件形态）时，**测试Agent 有权更新既有测试断言**（须在报告注明变更理由）；"禁止改源码/改冒烟"红线不变。
17. **设计文档=代码最新事实**：`/docs/design` 文档必须与代码同步；小改动直改并在「变更记录」块记录（日期+内容+原因）；大版本变更（如 v2→v3）归档原件、另立新版（详见 §12）。
18. **引用完整性**：注册表（MODULE_REGISTRY.json 等机器引用）指向的文件必须存在——Phase 1 交付校验项；文档改名/移动后全库引用同步，断链=0。
19. **PASS with notes 回环**：评审"通过但附非阻断遗留"时，遗留必须回环（开发实现确认或明确搁置记录）；禁止永久悬挂。

## 十一、执行指南

### 场景识别与路由

收到用户需求后，首先根据"第九章 全生命周期场景路由"判断场景类型，然后确定路由路径：

1. **新建项目** → 从 Phase 1 开始全量执行
2. **新增模块** → 从 Phase 1（更新架构）开始局部重入
3. **删除模块** → 先分析依赖，无依赖则自动执行，有依赖则阻断
4. **需求变更** → 分级判断：绿/黄/红
5. **性能优化** → 绿色增强版路径
6. **依赖升级** → 红色全量重构路径
7. **纯配置变更** → 绕过主流程，仅改配置
8. **版本回滚** → 紧急通道
9. **只读查询** → 只读模式，不生成变更

### Phase 执行规范

每个 Phase 执行时，加载对应的角色 prompt 文件：

- **Phase 1** → 加载 `prompts/architect.md`（架构师角色定义）

- **Phase 3** → 加载 `prompts/reviewer.md`（评审员角色定义）
- **Phase 4** → 加载 `prompts/developer.md`（开发Agent角色定义）
- **Phase 5** → 加载 `prompts/tester.md`（测试Agent角色定义）

- 架构文档使用 `templates/architecture.md.template` 渲染

## 十二、工程文档治理规范（文档生命周期 · v1.3 新增）

### 12.1 设计文档=代码最新事实（强制）

- `/docs/design` 下的文档**必须等于代码当前事实（最新版）**；禁止以"演进说明指向别处"替代正文更新（两套机制职责不同：`演进说明`=快速识别已失效段落；`变更记录`=追溯变更原因）；
- **小改动（机制内演进/内容增删）**：直接在原文修改，并在文档头部「> 变更记录:」块逐条追加（`日期 + 变更内容 + 原因`）；文档头部统一元信息块：

```
> 版本: <体系+完成态>（如 V3 UI M4 完成态 / V3 早期 完成态（仅追溯））
> 日期: <git 追溯的实质修改日——跳过文档整理/重命名类提交>
> 目标读者: <维护语境，如 V3 接手开发者（前端 UI 维护）>
> 变更记录:
>   - <日期>：<变更主题（来源 git log 实质提交）>
> 维护规则：设计文档与代码同步（最新版）；小改动直改并记录，大版本变更时归档原件、另立新版。
```

- **大版本变更（v2→v3 / v3→v4 等架构级换代）**：涉及文档**全部归档**（`docs/archive/<新版本号>/`，版本头标「仅追溯 ⚠️ 勿作为实现依据」）→ **另立新版本文档**（新版本号后缀）；新旧追溯链双向标注（新：替代档案；归档索引：←被替代）。

### 12.2 命名与目录规范

- **后缀即时期**（全文档强制，入口/机器文件除外——README.md、MODULE_REGISTRY.json 保持固定名并内部标注时期）：

| 后缀 | 含义 |
|---|---|
| `-ui-v3` | 前端 V3 UI 现行 |
| `-data-v3` | 数据平台 v3 现行（与 -ui-v3 对称） |
| `-v3-early` | V3 早期版本（v3.1-v3.3 时代，被替代 · 仅追溯）——**禁用意义不明后缀（如 -legacy）** |
| `-v2` | V2 时期 |
| `-v3` | 项目级 v3 现行（架构/手册/方案） |

- **目录分层**：`docs/design/{frontend,backend}/` 只放现行；`docs/archive/<版本号>/{frontend,backend}/` 按版本号分层归档（未来随版本新增 `v4/` 等）；每层维护 `README.md` 分类索引（含"← 被什么替代"映射与归档规则：时间冻结、仅更新版本头）。

### 12.3 治理动作清单

1. 文档治理/改名 → 全库引用同步（含历史评审/QA/bug 报告中的**路径引用**）且**仅同步引用、不回溯改写审计内容**；
2. 注册表引用校验：`design_doc`/`architecture_doc` 指向文件必须存在（Phase 1 交付校验项）；
3. 归档件内容冻结；确认无价值 → `docs/archive/` 永久保留或移除（经用户确认）。

## 十三、依赖升级执行模板（v1.3 新增 · 对齐"依赖升级=红色全量重构"）

| 步骤 | 动作 | 验证 |
|---|---|---|
| 0 | 打基线 tag（如 `v3-ui-m4-base`，全量回退点） | — |
| 1..N | 每项升级 = 独立 commit（`chore(m4-upgrade-<包>)`） | 单项失败 `git revert` 该 commit，**不阻塞其余项** |
| 每项 | 升级命令 + **工具链连带**（vite↔vitest 等版本映射一起升） | `npm ls` peer 校验（deduped）+ 构建 |
| 行为级判定 | **验证"行为级"而非"build 绿即可"**——如 Tailwind 4：产物 CSS 含目标工具类 = 通过（防 build 过但视觉崩）；React 19：`useRef<T>()` 无参重载移除等 API 断点清单 | 全量测试 + 针对性验证命令 |
| 收尾 | 已知项**如实记录不豁免**（如 Lighthouse 环境受限 → 替代指标入档）；升级清单/回退表/已知项写入用户手册 | QA 报告含限制说明 |
